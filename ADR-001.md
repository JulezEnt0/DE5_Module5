# ADR-001: Adopt a medallion architecture for the library data pipeline

**Date:** 12/10/2026
**Status:** Accepted

## Context

Newham Public Library Network collects data from four sources in different formats: circulation (CSV), events (JSON API), member feedback (text files) and the digital catalogue (Excel). Analysts currently spend about 60% of their time cleaning data, and manual consolidation takes 2-3 days per month. There are no automated quality checks, so duplicates, missing values and inconsistent formats reach analysis.

The pipeline diagram shows how raw files move from the sources, through ingestion and cleaning, to analysis-ready outputs.

## Decision

We will use a medallion architecture with three layers:

- **Bronze:** raw data from all four sources, stored exactly as received with an ingestion timestamp.
- **Silver:** data cleaned and validated by our Python package. Records that fail validation checks are sent to quarantine and trigger alerts, rather than being silently dropped or passed on.
- **Gold:** analysis-ready aggregations that answer the library's key questions: popular books by borough, member retention rate, and event impact on visits.

Gold outputs feed Power BI, where row-level security restricts branch-specific data.

## Reasons

- **Separation of concerns:** ingestion, cleaning and aggregation are separate steps, so each can be built, tested and changed independently.
- **Reprocessing:** keeping raw data untouched means we can fix cleaning rules and rerun without re-requesting data from the source systems.
- **Quality enforcement:** validation happens at one defined point (bronze to silver), so the quality requirements (e.g. under 1% missing ISBN) can be checked automatically and consistently.
- **Handles mixed formats:** all sources land in bronze regardless of format, so the pipeline has a single entry point.
- **Reduces manual effort:** automating cleaning and consolidation targets the 60% of analyst time currently spent on cleaning.
- **Industry standard:** the pattern is well understood and maps directly onto Microsoft Fabric lakehouse layers.

## Consequences

**Positive**

- Raw data is always preserved in bronze, so we can reprocess if cleaning logic changes.
- Silver is the trust boundary: gold always reads from silver, never bronze.
- Failed records are quarantined and alerted on, so data issues are visible and traceable to a source.
- Security can be applied per layer: restricted access to bronze (raw member data) and row-level security on gold.
- Cleaning logic lives in one Python package, which can be unit tested and deployed through CI/CD.

**Negative / trade-offs**

- Storing three copies of the data increases storage use and pipeline complexity.
- Quarantined records need someone to review and fix them, so we need an owner and a process for this.
- Unstructured feedback text needs extra processing in silver before it can be analysed.
- Any change to a schema in a source system needs to be handled at the bronze-to-silver step.
